# 通过 SSH 端口转发访问工作台

Narracut 的本地 HTTP 服务没有媒体鉴权，必须继续只绑定 `127.0.0.1`。远程访问应使用 SSH 回环端口转发，不要把服务改为监听 `0.0.0.0`：

```bash
ssh -o Compression=no -N -L 3579:127.0.0.1:3579 <远程主机>
```

Windows 主机随后访问 `http://localhost:3579`。MP4、JPEG 等媒体通常已经压缩，SSH 再压缩几乎不能减少流量，反而会增加 CPU 和排队开销，因此视频工作负载建议关闭 SSH 压缩。

工作台列表只允许请求 `/api/assets/thumbnail` 返回的首帧 JPEG，不应为缩略图请求 `/media/*.mp4`。打开 Asset 完整预览、选择视频 Scene 或实际播放仍会读取原 MP4，并继续受 SSH 带宽、往返时延和丢包影响；低码率 Preview Proxy 不在当前方案范围内。

## 网络排查

本次卡顿诊断中，当前 SSH 连接观察到累计约 3.6%–4.1% TCP 重传。该数值不是应用指标，但足以放大多路 MP4 Range 请求的停顿。应用侧首帧修复消除了列表后台视频读取，不能代替网络修复。出现主动视频播放卡顿时应同时检查：

- Windows 到 SSH 主机的延迟、丢包和 Wi-Fi 稳定性；
- SSH 连接的 TCP 重传是否持续增长；
- VPN、代理或 MTU 是否造成分片/丢包；
- 原视频是否为 fast-start MP4（`moov` 位于文件头）。

可在远程主机用 `ss -tin` 观察 SSH 连接的 `retrans`、RTT 和拥塞窗口，并用连续的 `ping` 与 Windows 侧结果交叉验证。网络调优完成后仍应保留应用侧缩略图服务，因为它从根源上避免了列表对原视频的无意义读取。
