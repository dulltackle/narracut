# 当前 Codex 对话的工作台面板

## 能力依据与入口

打开、重试、接管项目或驱动当前对话创作时，使用[插件工作台技能](../plugins/narracut/skills/narracut-workbench/SKILL.md)。技能负责核对当前对话身份、启动 `panel.mjs`、调用实际可用的宿主面板工具及持续驱动创作步骤；构建与安装见[插件打包](plugin-packaging.md)。

面板创建结果与宿主展示结果分别核对：`prepared` 只表示服务就绪，`queued` 只表示宿主排队；实际显示需要观察页面与桌面位置。秘密面板 URL 只供当前会话使用，不进入文档、issue 或共享证据。

工作区、任务与控制权约束见[规范第 2 节](spec/project-vnext.md#2-产品边界与工作区)和[第 8 节](spec/project-vnext.md#8-agent-创作任务)。实现入口为[面板服务](../plugins/narracut/src/workbench-panel.ts)、[项目控制权](../plugins/narracut/src/project-control.ts)与[创作任务](../plugins/narracut/src/creation-task.ts)。

## 当前 Agent 直接驱动创作（#99 修复）

生产工作台使用 [CurrentConversationHost](../plugins/narracut/src/current-conversation-host.ts)，通过当前对话的面板 RPC 交换 `creation_step`。独立 `CodexAppServerHost` 只用于固定宿主探针与协议测试；生产创作不启动独立模型进程或向另一个 App Server 请求 `thread/resume`。

步骤的调用顺序、身份核对、图像审阅与回执处理统一按插件技能执行。排查协议时须区分步骤接收与持久提交：`received` 不表示已落盘或交付；步骤只驻留内存，不扩展项目任务检查点。只读会话无权读取步骤能力；停止或接管撤销的是 Narracut 步骤，并不证明桌面 Codex Turn 已被中断。

当前 RPC 通道不能订阅桌面的原生停止/退出事件，也不能在 Scene 待办满足后自行唤醒已经结束的 Agent Turn。已观察到宿主错误且仍可调用工具时，可以显式报告中断；服务重启则按检查点加载为已停止。这些行为不替代规范要求的真实宿主生命周期验收。

### #123 按钮触发当前对话：已确认边界，待宿主验证

“同步内容并调整画面”的目标链路是工作台按钮提交明确请求，由当前控制对话的 Agent 继续同一 Agent 创作任务，调整候选 Render Program，并按 [#123](https://github.com/dulltackle/narracut/issues/123) 完成检查与发布。这里的同一任务指 Narracut 的任务身份与检查点；它可以跨多个 Codex Turn 继续，不要求一个模型回合常驻。首次无设计时的生成授权仍遵循 #123。

当前实现尚未打通唤醒环节：`CurrentConversationHost.startTurn` 只保存待领取步骤，面板桥只转发工具调用。独立 App Server 恢复活跃桌面对话曾出现写权冲突，见[真实验收记录](current-conversation-acceptance.md)；不能用已有适配器或方法名称推断自动触发已可用。

已确认以下交互边界：

- 宿主不支持自动触发时，允许明确标注的“复制指令，返回当前对话发送”替代入口；复制不表示已发送或任务已运行，替代入口不计作一次点击触发验收通过。
- 当前对话正在处理其他工作时，请求等待，显示“等待当前对话处理”；不强行打断当前工作，不另开模型进程。等待须有实际请求状态依据，不能用此文案掩盖宿主不支持。
- 真正执行前重新核对项目身份、控制权、任务与最新输入。等待期间再次编辑仍遵循重新选择更新方式的规则，迟到请求不能绕过该规则发布旧输入结果。

先验证最小宿主链路，再承诺自动触发：当前对话结束后，在真实工作台点击测试按钮，无需用户手动发送消息，同一对话开始处理请求并领取原任务步骤。记录宿主版本、对话与任务身份、请求回执及实际步骤领取；另验证忙碌时等待、重复点击和等待期间输入变化。仅观察到页面 RPC 成功、消息排队或测试替身消费步骤均不足以证明唤醒成功。本节记录已确认边界，不声明该探针或完整创作链路已经通过。

#### 2026-09-14 UTC：真实内置浏览器消息入口探针

结论：**消息入口验证受阻，完整自动唤醒未执行。** 基线 `6a8178b08f9abaa6ce2d7dbd77b707c3baff8f84`，先运行 `pnpm build:plugin` 成功，再从已核对的当前对话启动空工作台。Shell 的对话身份与 `read_thread` 一致；`open_in_codex` 返回 queued，随后使用真实 Codex 内置浏览器打开同一面板并看到启动台。该观察不证明 queued 面板的桌面外层位置。浏览器报告 Linux、Chrome 152；本次未取得 Codex 应用版本，不把浏览器版本当作宿主版本。

- 顶层为浏览器顶级页面，`window.openai` 和 `sendFollowUpMessage` 均不存在。内部工作台的 `window.openai` 只有 `selectDirectory`、`selectFile`、`selectFiles`，没有消息发送接口。
- 在工作台 iframe 内临时添加探针按钮，从该 iframe 的执行上下文向同源父页面发送 `ui/initialize` 与 `ui/message`。握手返回 `protocolVersion: 2026-01-26`、`hostInfo: { name: narracut-local-panel, version: 1 }`、空 `hostCapabilities` 和 `hostContext`；`ui/message` 在 5 秒观察窗内无回执。代码核对表明该父页面仅处理初始化、同步与工具调用，没有向桌面宿主转发消息的分支。
- 探针消息只要求回复收到标记 `NC-WAKE-123`，不要求创作或修改文件；本次 `read_thread` 快照未出现该标记的新用户消息。未调用 Agent 侧 `send_message_to_thread`，避免用另一条通道冒充页面触发。
- 首轮探针误在父页面上下文创建处理函数，初始化也无回应，已排除为无效样本；校正为 iframe 内脚本后取得上述握手。无回执本身不等于证明所有宿主消息能力都不存在，结论仅限当前 Narracut 浏览器面板集成。
- 空闲 Turn 唤醒、忙碌请求排队、同一任务领取步骤、重复点击幂等和等待期间输入变化均未进入验收；本次没有创建视频项目或创作任务。临时按钮与脚本在验证后通过重载移除，未修改生产代码。

后续需先找到并验证当前桌面宿主明确提供给页面的消息桥，再补齐上述完整链路；当前不能把 `ui/message` 发给本地面板便当成已经通知 Codex。

### 真实桌面关闭／重开复验步骤

1. 从当前 Codex 对话核实身份，按插件工作台技能打开测试项目，在本地保留秘密服务 URL，记录项目目录、Project ID 和当前 Task ID。
2. 在当前对话明确发起一项会修改候选资源的创作；在 Agent 工作区确认“运行中”，记录候选 baseline 和最后保存阶段。
3. 使用 Codex 右侧面板自身的关闭入口关闭工作台，保持 Codex 应用、当前创作和服务进程运行。不要发送“停止任务”，也不要终止服务。
4. 等待当前对话产生新的持久成果。通过同一服务 `get_workbench` 读取任务和候选，记录 Task ID、候选 baseline，以及候选目录中实际新增或修改的文件内容。
5. 在同一对话用 `open_in_codex` 重新打开原 URL；观察先同步再显示最新内容。核对 Project ID、Task ID、最新候选和控制权；确认没有新任务、自动播放、自动接受或自动 Render。
6. 从另一对话打开同一项目，核对“只读 · 项目由另一对话控制”与禁用写操作；原任务和控制权保持不变。
7. 分别以用户明确停止、Codex 中断、退出并重启应用进行对照。重开应显示实际停止原因和保留成果，只有明确继续才再次运行；记录每种情况的 Task ID 与原因。
8. 记录验收日期、Codex 版本、对话身份、截图路径、候选文件证据和每步结果。真实模型不可用、额度不足或无法操作桌面关闭入口时，将对应步骤标为“未执行”，不得用自动化替代通过。
