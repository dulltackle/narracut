# 07 — 渲染管线与前后端边界

Type: grilling
Status: open
Blocked by: 02

## Question

前端 SPA 与本地 Node 服务的职责怎么切，渲染怎么真正跑起来。

1. **职责划分**：Node 服务负责什么（读写 `project.json`、素材文件服务、TTS 代理以藏住 key、触发渲染、进度回传），前端负责什么。边界要能一句话说清，不能含糊。
2. **素材的双通道访问（核心，依赖 02 第 7 条）**：Player 走 http、renderer 走文件系统。服务怎么暴露素材目录、DSL 里存什么、两条通道怎么保证指向同一个文件。这是「Preview = Render」在工程上最容易裂的地方，本票必须给出确定方案。
3. **渲染怎么跑**：同进程 / 子进程 / 单 worker？渲染期间还能不能继续编辑（能的话，编辑的是内存里的哪一份）？
4. **进度回传**：轮询还是 SSE。渲染要多久（02 第 5 条给量级）决定这里做多重。
5. **Render Snapshot**：单文件模型下，快照就是复制一份 JSON——复制到哪、怎么和产出的 MP4 关联、留几份。
6. **失败定位到 Scene**：PRD 第 34 节要求错误必须指出是哪个 Scene。renderer 抛出的错误能不能带上 Scene 信息？如果不能，用什么办法反推（帧号 → Scene 的映射）。
7. **应用怎么启动与分发**：一条命令起前后端？打包形态是什么（npm 脚本 / Electron / 别的）？单用户产品这一条不能含糊——它决定用户第一次能不能把这东西跑起来。
8. **TTS key 存哪、怎么读**：不能进 `project.json`（那是要能分享/版本化的），也不该硬编码。

## 依赖说明

**02 已经把三件事定死了，本票不要重开，直接采纳**：

- **素材寻址**：DSL 存相对项目根的相对路径，Node 服务把项目根整体映射成本地 HTTP（动态端口），端口/URL 绝不落进 DSL，Player 与 Composition 共用同一个「相对路径→URL」函数。报告第 7 节有完整可跑代码（静态服务 + Player 端 + `selectComposition`/`renderMedia` 端），第 2 条剩下的只是把它落成本项目的接口。
- **渲染必须异步**：官方没有任何"N 倍时长"的经验法则，耗时随机器和编码参数大幅波动。第 3、4 条据此设计，不要再考虑同步渲染。
- **字体**：`loadFont()` 显式加载、字体文件放 `public/`、禁止依赖系统字体。

**与 09 的关系**：如果 09 号票决定导入时自动转码，转码跑在哪个进程、怎么报进度，归本票管——但不构成阻塞，先按"暂不转码"设计边界，09 有结论后再补一个挂载点。
