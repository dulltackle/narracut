# 06 — DSL schema 定稿

Type: grilling
Status: open
Blocked by: 03, 05

## Question

`project.json` 的完整结构定稿——这是系统的核心数据资产，也是最难改的东西。

1. **顶层结构**：`version`、项目元信息（名称、fps、分辨率）、`scenes[]`、`assets[]`。素材是集中登记还是内联在 Scene 里？
2. **Scene 的字段**：id（怎么生成、稳不稳定）、narration、visual、asset 引用、motion、时长相关字段（依赖 05）。
3. **四个 Visual Type 的字段**（依赖 03 的视觉定稿）：用 discriminated union（每个 type 一套自己的字段）还是扁平的可选字段？前者严谨、后者改 type 时不丢数据——这是个真取舍，`Image → Metric` 这类切换在 PRD 里是核心用例。
4. **素材引用怎么存**——**02 已定：相对项目根的相对路径**，端口和绝对路径都不进 DSL，所以项目文件夹整体移动不会失效。本票只剩下：坏引用（素材被删或改名）怎么在 DSL 层面表示、打开项目时的完整性校验产出什么结构（02 建议报错要带「Scene ID + 相对路径 + 尝试解析的绝对路径」）、要不要额外存内容哈希来识别"文件还在但被换了"。
5. **TTS 音频的位置与关联**：生成的音频存哪、DSL 里怎么引用、怎么表达它与 narration 文本的对应关系（配合 05 第 5 条的 stale 判定——是存文本哈希还是别的）。
6. **派生字段**：`startFrame` 等确定不落盘的话，校验与渲染各自在哪里算、由谁保证一致。
7. **version 与迁移**：V1 只有 `1.0`，但迁移机制现在就要定好——读到未知版本怎么办、迁移函数放哪、怎么保证旧项目永远打得开。
8. **AI 可生成性实测**：把 schema 喂给 LLM，要它生成一条合法的 20 句 DSL，看它在哪些地方出错。PRD 的核心原则之一是「可 AI 生成」，这一条**必须实测一次**再定稿，不能只在原则里写着。常见坑：discriminated union 判别字段、必填与可选的边界、id 的引用完整性。
9. **Zod schema 定稿**，以及校验在什么时机跑（保存前？渲染前？两者都跑？）。

## 依赖说明

- **03** 定下四个 Visual Type 各自需要哪些内容字段。
- **05** 定下时长相关字段的语义与哪些字段落盘。

## 产出

`project.json` 的完整示例（就用 04 号票的真实文案，写成一条完整的 20 句项目）+ Zod schema，结论回填本票 `## Answer`。
术语写进 `CONTEXT.md`。如果「DSL 与 Remotion 解耦」这条原则在实践中被迫让步，写一条 ADR 记下为什么。
