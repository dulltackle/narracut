# 05 — 时间模型定稿

Type: grilling
Status: open
Blocked by: 01, 02, 04, 08

## Question

Scene 的时间语义，精确到可以直接写成函数。

**已定的前提**（charting 会话敲定，本票不重开）：只有 Cut；Duration 的主人是旁白音频；素材长了截断、短了冻最后一帧。

本票要把这些原则变成没有歧义的规则：

1. **Duration 的精确定义**：等于 TTS 音频时长本身，还是 `音频时长 + startPadding + endPadding`？PRD 有 padding 这两个字段，V1 到底留不留——留了就得回答默认值是多少、为什么。
2. **TTS 自带静音怎么处理**：如果 01 号票发现音频头尾自带静音，要不要裁掉？不裁的话，20 句累积下来整条片子会拖多久，观感能不能接受。
3. **秒 → 帧的取整（核心）**：TTS 给的是小数秒，30fps 下必须落到整帧。逐句取整，20 句的累积漂移最坏是多少？改成「累积后取整」则每句边界不落整帧。**定一个规则，并明确给出音画同步误差的上界**——这个上界要能说服人，不能"应该没问题"。
4. **手填与自动回填的优先级冲突（核心）**：PRD 说「手动修改后以用户输入为准」。但用户手填 4s、TTS 音频是 6s，旁白就会被硬生生截断——这是产品级的错误，不是用户想要的。这个冲突怎么解？可选方向：手填只能加不能减、手填时给出警告、手填被记为 `durationOverride` 且渲染时取 `max`、或者干脆不允许手填。定一个，并说明代价。
5. **文本改了但没重新生成语音**：这时 Scene 是什么状态？音频和文本不同步是默许的常态，还是要显式标记为 stale 并在 UI 上警示、在渲染前拦截？
6. **缺素材 / 缺音频的 Scene**：时长是多少、画面是什么。这是编辑过程中的常态（先写完 20 句再逐句配素材），不是异常，必须有明确定义。
7. **产出**：`startTime / startFrame / durationInFrames` 的计算函数定义。PRD 主张它们运行时派生、不落盘——确认这一点，并说明 DSL 校验、Player、renderer 三处各自在哪一步调用它。

## 依赖说明

- **01** 给出音频时长的来源与协议事实：`extra_info.audio_length` 直接返回毫秒时长；TTS 另有显式停顿标记 `<#x#>`（0.01–99.99s），这意味着**停顿是可以主动控制的**，第 1 条的 padding 设计要把这个手段考虑进去。
- **08** 给出实测数字：句首尾静音的实际时长、`audio_length` 与真实解码时长的误差 → 直接决定 1、2、3 能不能成立。头尾静音若稳定存在，第 2 条就不是"要不要裁"而是"裁多少"。
- **02** 给出截断与冻帧在两侧的实现方式 → 决定这些规则可不可实现。
- **04** 给出真实素材的时长分布 → 决定「冻帧」是兜底还是常态，若是常态则整条规则要重来。
